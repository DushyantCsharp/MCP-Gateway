# Datasheet: mcp-customs detection benchmark, v1

Following the questions in *Datasheets for Datasets* (Gebru et al., 2018).
Exact counts and hashes for any build are in `build/manifest.json`.

## Motivation

To measure how well a detector in the gateway catches prompt injection
hidden in tool output, and how often it wrongly flags legitimate output.
Both numbers matter: a detector that flags everything catches every attack
and is useless. The benign side is deliberately hard for that reason.

## Composition

| Class | Label | Samples (v1) | Groups | Source |
| --- | --- | ---: | ---: | --- |
| `tool_hijack` | attack | 1,020 (510 base, 510 enhanced) | 30 instructions | InjecAgent "direct harm" cases |
| `exfiltration` | attack | 1,088 (544 base, 544 enhanced) | 32 instructions | InjecAgent "data stealing" cases |
| `paired` | benign | one per line in `benign/fill-in.md` | 17 templates | InjecAgent's tool-output templates, slot filled with ordinary hand-written content |
| `security_docs` | benign | 102 | 5 documents | paragraphs of this project's documentation, which discusses prompt injection, tokens and exfiltration |
| `code` | benign | 78 | 17 modules | CPython standard-library functions whose source contains words such as `ignore`, `password`, `send`, `execute` |
| `long_outputs` | benign | 90 | 90 | seeded synthetic ledgers, search results and web-server logs |

Each sample is one tool output. Attack samples are InjecAgent's `Tool
Response` field: a realistic tool result (an email, a review, a note) with an
attacker's instruction inside one field. `base` and `enhanced` hold the same
attack; `enhanced` adds InjecAgent's fixed persuasion prefix.

## Collection

- **InjecAgent** (MIT), fetched at a pinned commit; see `SOURCES.md`. Its
  authors generated the cases by crossing a small set of attacker
  instructions with tool-response templates.
- **Paired benign** fillers are written by hand into `benign/fill-in.md`,
  following the guidance at the top of that file: ordinary content for the
  field, including everyday requests addressed to people.
- **Docs, code and long outputs** are generated by `build.py` from files in
  this repository, the local CPython standard library and a fixed seed.

## Preprocessing and splits

None of the text is altered. Samples are split by **group**, never one by
one: about 30% of groups go to `test`, chosen by a hash of the group name.
For InjecAgent the group is the attacker instruction, because each
instruction appears in 17 templates. A per-sample split would put every
instruction in both halves, and a detector tuned on `dev` would be scored on
attacks it had effectively already seen. The build refuses to write if any
group appears in both splits.

`dev` is the only split any threshold or rule may be chosen on. `test` is
reported, never tuned on.

## Known limitations and biases

- **Few distinct attacks.** 2,108 attack samples, but only 62 distinct
  attacker instructions. The test split holds 16 of them: 11 tool-hijack and
  just 5 exfiltration. Per-category rates swing with which instructions land
  in test (exfiltration differs by 16 points between dev and test in the
  first run), and the intervals are wide. Read them as an early signal.
- **Coverage.** Only two attack categories, both injected into a single
  field of a short structured tool result. Not covered yet: instructions in
  long retrieved documents, obfuscated payloads (encodings, look-alike
  characters, text split across fields), multi-step attacks across turns,
  and non-English text. These are planned for the next release.
- **One format family.** InjecAgent's tool outputs are Python-style
  dictionaries. The `paired` class shares that format on purpose, so format
  alone does not separate the classes.
- **Synthetic long outputs** are more repetitive than real ones. Repetitive
  text is a known weakness of the classifier now in use, so this class may
  overstate its false-positive rate on real logs, or understate it on worse
  ones.
- **Hand-written fillers** reflect one author's sense of ordinary content.

## Uses

To compare detectors and track one detector across releases, always on the
`test` split, with intervals. Not for training a detector: the attack side
is too small and too templated, and training on it would invalidate the
benchmark.

## Distribution and maintenance

The built JSONL files are not committed. They are regenerated from the pinned
sources by `uv run python bench/datasets/build.py`. The manifest (inputs and
output hashes) is committed with each published result, so a result can be
tied to its exact data. New sources are added to `SOURCES.md` first, with
their licence.
